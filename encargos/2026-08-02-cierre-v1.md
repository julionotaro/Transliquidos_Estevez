## PIEZA 1 — Cliente no reconocido falla ruidoso

### El problema

En la corrida real, gpt-4o leyó el cliente como **"FORBA"** (misread de "FORESA"). Como `regimenIndexacion` solo reconoce FORESA/BRESFOR, le asignó `linea` en vez de `agregada_quincenal`, que es el que le correspondía por D-06.

**Un cliente mal leído asignó el régimen de indexación equivocado sin que nadie se entere.** Es el mismo patrón que venimos combatiendo en todo el proyecto: el error que pasa como dato bueno.

### La solución — NO es un alias

**No agregar "FORBA" como alias de FORESA.** Un alias por cada misread convierte un error de lectura en regla de negocio, y mañana aparece "FORESAA" o "FORFSA". Cada alias es una puerta silenciosa.

**Lo correcto:**

```
Lista de clientes conocidos: FORESA, BRESFOR, QUIMIDROGA, RNM, HELM, BALTRANSA
(más los que ya estén cableados en el código — inspeccionar y usar la lista real)

SI cliente_leido ∈ CLIENTES_CONOCIDOS:
    asignar regimen_indexacion normalmente
SINO:
    regimen_indexacion = null
    estado_lectura = REVISAR
    motivo = "cliente_no_reconocido: {valor_leido}"
```

**El motivo debe incluir el valor leído**, para que quien revise vea "FORBA" y entienda de inmediato que es un misread de FORESA, sin tener que abrir el escaneo.

`CLIENTES_CONOCIDOS` va como lista configurable en un solo lugar, no como condiciones dispersas. Cuando TLE sume un cliente nuevo, se agrega ahí y nada más.

### Tests
- Cliente "FORESA" en Caldas→Orense → `agregada_quincenal` (no cambia).
- Cliente "FORBA" → `regimen_indexacion` null + REVISAR con motivo `cliente_no_reconocido: FORBA`.
- Cliente null (no se leyó) → mismo tratamiento, motivo indicando que no se leyó.
- Cliente conocido con régimen `linea` → sin cambios (no regresión).
- BALTRANSA → `incluida` (no cambia).

## PIEZA 2 — Vista de pendientes

### Qué es y qué NO es

**Es** una lista consultable de todo lo que quedó esperando algo. Lo mínimo para que una persona sepa qué reclamar y a quién.

**No es** el tablero de Fase 4 (edición inline, corrección de campos, flujo de resolución). Eso viene después. Acá solo se mira.

### Contenido

Una fila por viaje pendiente, con:

| Columna | De dónde sale |
|---|---|
| Fecha de carga | `viajes.fecha_carga` |
| Chofer | `viajes` / hoja |
| Cliente | `viajes.cliente` |
| Ruta | origen → destino |
| Qué falta | `pendiente_falta` |
| A quién reclamar | `pendiente_reclamar_a` |
| Días esperando | derivado de `createdAt` |
| Motivo de revisión | `motivo_revision` (para los REVISAR de lectura) |

**Incluye ambos casos:**
- `PENDIENTE_DOCUMENTACION` — falta documentación.
- `REVISAR` — la lectura fue dudosa (incluye el nuevo `cliente_no_reconocido`).

**Orden por defecto:** días esperando, descendente. Lo más viejo primero — es lo que más urge reclamar.

### Forma

**La más simple que funcione.** En orden de preferencia:

1. Si ya existe una pantalla de Control que pueda extenderse → extenderla.
2. Si no, una página HTML estática servida como la de ingesta, que consulte por webhook.
3. Si eso resulta grande, una consulta que devuelva JSON y un HTML mínimo que lo renderice en tabla.

**No construir un frontend elaborado.** Sin framework, sin build. Tabla legible, ordenable si sale gratis, nada más. El criterio es que alguien de la oficina pueda abrirla, ver qué falta y llamar por teléfono.

### Tests
- Un viaje `PENDIENTE_DOCUMENTACION` aparece con su falta y a quién reclamar.
- Un viaje `REVISAR` por `cliente_no_reconocido` aparece con el valor leído visible.
- Los días esperando se calculan bien.
- Un viaje completo y OK **no** aparece.
- La lista vacía no rompe (no hay pendientes → mensaje claro, no error).
